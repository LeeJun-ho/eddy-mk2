## 기본 지침

### 1. 코딩 전에 생각하기

**가정하지 않는다. 혼란을 숨기지 않는다. 트레이드오프를 드러낸다.**

구현 전에:

- 가정하는 내용을 명시적으로 밝힌다. 불확실하면 질문한다.
- 여러 해석이 가능하면 제시한다. 조용히 하나를 선택하지 않는다.
- 더 단순한 접근이 있으면 말한다. 필요하면 반론을 제기한다.
- 불명확한 부분이 있으면 멈춘다. 무엇이 헷갈리는지 명시하고 질문한다.

### 2. 단순함 우선

**문제를 해결하는 최소한의 코드. 추측성 코드는 없다.**

- 요청한 것 이상의 기능은 추가하지 않는다.
- 단일 사용 코드에 추상화를 적용하지 않는다.
- 요청하지 않은 "유연성"이나 "설정 가능성"은 넣지 않는다.
- 발생할 수 없는 시나리오에 대한 에러 핸들링은 작성하지 않는다.
- 200줄로 작성했는데 50줄로 줄일 수 있다면 다시 작성한다.

스스로 물어본다: "시니어 엔지니어가 이걸 보고 과하다고 할까?" 그렇다면 단순하게 만든다.

### 3. 최소 범위 수정

**반드시 필요한 것만 수정한다. 자신이 만든 문제만 정리한다.**

기존 코드를 수정할 때:

- 인접한 코드, 주석, 포맷을 "개선"하지 않는다.
- 문제없는 코드를 리팩토링하지 않는다.
- 자신이라면 다르게 하더라도 기존 스타일을 따른다.
- 관련 없는 데드 코드를 발견하면 언급만 한다. 삭제하지 않는다.

수정으로 인해 사용되지 않는 코드가 생긴 경우:

- 자신의 변경으로 인해 사용되지 않게 된 import/변수/함수는 제거한다.
- 기존에 있던 데드 코드는 요청이 없으면 건드리지 않는다.

기준: 변경된 모든 줄은 사용자의 요청에서 직접 추적 가능해야 한다.

### 4. 목표 기반 실행

**성공 기준을 정의한다. 검증될 때까지 반복한다.**

작업을 검증 가능한 목표로 전환한다:

- "유효성 검사 추가" → "잘못된 입력에 대한 테스트를 작성하고 통과시킨다"
- "버그 수정" → "버그를 재현하는 테스트를 작성하고 통과시킨다"
- "X 리팩토링" → "리팩토링 전후 테스트가 모두 통과하는지 확인한다"

여러 단계의 작업은 간략한 계획을 먼저 제시한다:

```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

명확한 성공 기준이 있으면 독립적으로 반복 실행할 수 있다. 모호한 기준("되게 해줘")은 지속적인 확인을 필요로 한다.
